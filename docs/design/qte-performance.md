# QTE 时延设计与验收

[架构说明](architecture.md) · [当前状态](../development/status.md)

截至 v0.2.0，文件日志已后台写入，机制规则已有职责拆分，基础等待校准与离线局部基准可用；完整游戏端到端时延基线尚未建立。低时延是架构与行为变更的验收条件。

首轮迁移的 AST 一致性检查是历史证据，不能据此声明后续蓝区与机制改动仍和旧版完全相同。当前普通输入保留默认驱动时序，显式调整按住/松开等待时使用可取消分段等待。本文区分已有实现和待测目标，对应源码入口见[开发指南](../development/guide.md)。

## 关键执行路径

QTE 控制保持在同一个工作线程中，直接调用：获取最新有效 ROI → 提取特征 → 综合机制并决策 → 取消/窗口校验 → 提交输入。模块边界不等于线程边界，不将每一步包装成排队任务、通用事件、网络请求或跨进程消息。

app 负责进入和退出玩法，UI 展示快照；两者不逐帧参与按键决策。机制处理器复用同帧图像与必要特征，不为每种机制重新截图、重复颜色转换或调用整套 OCR。只有当前模式需要的检测器参与计算；若降频检测，必须定义观察有效期及重新检测条件。

配置解析、模板加载/缩放、OCR 模型初始化和必要预热在时序敏感的 QTE 开始前完成。模板和配置缓存属于本次会话，窗口几何变化使旧 ROI 失效，不能为复用缓存绕过现有窗口保护。

## 时延如何计量

不能只报告算法 FPS 或平均循环时间。应使用同一高分辨率单调计时来源，逐段记录少量数值；汇总和格式化移到循环外。Python 的 `perf_counter_ns` 适合短时段测量；时间单位为纳秒不意味着实际精度达到纳秒。`sleep` 的实际暂停还可能超过请求时间。[Python 时间接口](https://docs.python.org/3.12/library/time.html)

| 指标 | 定义与用途 |
| --- | --- |
| 帧源时间与取得时间 | 能获取源帧时间时同时记录；只在 grab 返回后打点无法确定画面真正年龄 |
| 有效新帧间隔 | 相邻不同源帧的间隔，识别重复帧、无新帧与采样空档 |
| 采集、识别、决策耗时 | 各段起止时间，定位具体计算与等待 |
| 决策到首次输入提交 | 包含反馈记录、锁等待、保护检查及驱动前置开销 |
| 源帧到首次输入提交 | 有源帧时间才能报告完整值；否则明确只测了 grab 返回到提交的部分 |
| 输入调用生命周期 | 分别记录按下提交、松开提交、调用返回和恢复采样；三者时延不能混用 |
| 停止响应 | 停止请求到输入释放，以及工作线程退出的时间，分别统计 |
| 后台负载影响 | 诊断、OCR、UI 和证据编码开启后，以上指标的变化 |

操作系统接受输入不等于游戏已经处理输入。游戏反馈可作为关联证据，但其呈现还包含游戏自身处理与渲染延迟，不能用一个“按键前”时间戳声称测出了完整响应。

每项记录样本数、p50/p95/p99、观察到的最大值和超预算次数，分别覆盖普通模式、快速指针、窄命中区与已支持的机制组合。长运行的偶发停顿不能被平均值掩盖。

时限由可操作窗口确定。局部速度近似稳定时，可用有效命中区宽度除以指针速度估算时间窗口，再扣除识别误差、采样相位和游戏接收延迟余量；存在反弹或突变时不能沿用匀速估计。采样间隔和处理时延需要一起计入。

具体毫秒预算在目标机器、帧率、分辨率和真实样本上建立基线后填写，作为后续变更门槛；不能凭“循环设为 10 ms”承诺端到端 10 ms。Windows/Python 运行下以测量和受控退化为依据，不声明硬实时保证。

## 并发、缓存与过载

### 检测频率与输入节奏分别控制

用户指出，现有等待可能用于适应不同机器和游戏处理速度，避免连续操作过快。这是需要保留并验证的设计考虑；仅凭源码中的 sleep 无法确认原作者意图，也不能断言游戏会覆盖、排队或忽略何种输入。

区分四种时间：截图检测间隔、一次按下到松开的持续时间、两次动作之间的最小间隔、等待游戏状态变化的超时。当前循环等待和驱动暂停可能同时影响这些时间；不能统一清零，也不能让所有动作共享一个任意固定延时。

目标是检测和决策及时，输入按动作约束执行。可以继续读取新画面而暂不发送新输入；一次按键提交不代表游戏已经消费它。动作应明确何时允许下一次输入：根据已验证的最小间隔、可观察的状态变化或二者组合。普通点击、绿色维持的按住/松开、破冰连续输入分别定义节奏；不能强制所有输入都等到反馈文字出现，反馈本身可能滞后或缺失。

固定等待可以提供处理余量，但不是游戏完成确认。对缺少可靠确认信号的动作，使用经实测的保守间隔和有限超时，避免无界重发；有确认信号时也需验证其识别可靠性。不同机器、游戏帧率和负载分别测量，必要时提供经过校验的时序配置范围。降低等待只能在确认按键接收、动作顺序和停止释放均可靠后进行。

- 主控制读取最新有效帧，不消费不断增长的历史帧队列。历史帧只用于轨迹分析和诊断；源帧不明或过期时不能伪装成新画面。
- 动作携带所属会话、帧/状态版本和有效期限，执行前核对。过期的瞬时点击不排队补发；停止所需释放和已持有按键的收尾另行处理，不能一起丢弃。
- 输入由一个控制任务所有；保护检查与停止优先于新动作。禁止为省时移除取消锁、失焦检测或释放逻辑。
- 按键不等待界面刷新、文件写入或低频信息读取。共享反馈锁只保护短小的内存更新，日志格式化、处理器调用和慢操作移出锁；改造时保留按键归属顺序。
- 记录只在热路径保存必要数值和有界证据引用/快照，复制成本也纳入测量。后台接收后使用拥有明确生命周期的数据，不能引用随后被相机覆写的缓冲区。
- 证据队列拥塞时丢弃或降低非必要截图采样并计数，不能阻塞输入。文件日志已使用 4096 容量并为 INFO 以上预留 256；过载仍可能丢失记录，由后台明确报告，不能宣称无损；UI 丢弃展示副本仍不能删除文件日志。
- QTE 期间暂停非必要的岛屿信息轮询；保留反馈/结算所需观察。OCR、OpenCV 和编码任务的线程数量及 CPU 使用需一并测量，“放后台线程”不等于不会争用资源。

Python 3.12 的常规 CPython 线程受 GIL 约束；原生库的并行行为还取决于具体实现。因此先测争用，再决定是否限频或限制库线程数，不默认每个机制开一个线程。[Python 线程说明](https://docs.python.org/3.12/library/threading.html)

超预算时先削减非必要诊断和查询工作，不自动关闭机制所需识别或盲目点击。旧动作失效后重新观察；持续无法满足时限则返回明确的时延不足状态并结束该任务。预测按键、修改输入驱动和减少按住时长是独立行为变更，须确认游戏接收和释放可靠性。

## 当前源码中的检查项

以下来自静态检查，不等于实测每次发生了对应时延，也不直接证明已有失败由此造成。

| 当前实现 | 需要测量或改造的边界 |
| --- | --- |
| 唯一默认配置中 `loop_sleep_seconds = 0.02` | 每轮显式等待 20 ms，此外还有采集、计算和输入耗时；不能称为 50 FPS 保证 |
| 默认 QTE 调用统一输入适配器的 `press("space")` | 保留旧驱动约 100 ms 按住、总计 200 ms 释放后暂停的请求时序；不是首次按下前必等 300 ms |
| 显式时序调用 `press_qte(hold, settle)` | 原生 keyDown/keyUp 不附加 PAUSE，按住和释放后等待可取消；等待不持输入锁，其他动作的全局暂停不改变 |
| 默认 `run_control.call_input` 在输入锁内调用驱动 | 默认驱动暂停仍会延长锁占用，需分别测量默认路径与自定义时序的停止响应 |
| `_press_qte` 先调用 `FeedbackSession.begin_press` | 输入前复制小图并向容量 128 的队列非阻塞提交；不等待观察锁，不整理归属或调用日志处理器，仍需测量复制和入队成本 |
| 文件日志后台输出 | 写盘已移到有界后台，保留结果/错误容量；消息固定、控制台/UI handler 与反馈锁仍需测量 |
| `_decision_captured_at` 在 grab 返回后记录 | 当前字段不能证明真实源帧时刻；新增测量需要标明时间戳语义 |
| GDI 观察还会执行定时 OCR | 需测量与控制线程同时运行时的资源争用，而非只跑空载算法基准 |

不在架构文档更新时直接把暂停清零：它同时影响按住时长、连续按键与游戏接收。首先确认实际运行参数，加入分段测量，再独立修改和回归。

## 验收次序

1. 在现有实现加入低开销计时，测量计时本身开销；保留环境、配置与源码版本。性能基线先于职责迁移建立。
2. 用固定真实帧序列和输入记录器比较识别/决策耗时与动作正确性，覆盖多机制及数据缺失。离线回放不用于声称 Windows 或游戏端到端耗时。
3. 在目标机器按相同条件比较重构前后，覆盖冷启动、持续运行、诊断开关、日志轮转、OCR 和证据队列压力，检查高分位时延和停止响应。
4. 新机制上线必须同时通过功能样本和性能预算；阶段重构不能只通过普通单元测试就宣称性能无回退。实机按键验证单独执行并记录授权范围。

目前已有合成图像与日志的离线局部基准，命令和测量范围见[开发规范](../development/standards.md)。完整截图、输入、反馈和停止响应基线仍未完成，不能由局部基准推导游戏已满足时限。
