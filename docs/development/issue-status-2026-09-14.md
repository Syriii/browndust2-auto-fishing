## 新审查问题是否需要修复

本次重新运行原有隔离复现，R1—R8 仍成立。所有输入与截图依赖均为 mock；没有清包、钓鱼或操作真实游戏。具体反例、位置和测试要求以审查报告为准。

| 顺序 | 项目 | 必要性与边界 |
| --- | --- | --- |
| 优先 | R1 手动清包保护、R2 出售页面确认 | 涉及输入目标和出售流程，应修。R1 影响手动工具，不能误说主界面完全没有前台保护；R2 是可复现的误操作风险，本轮没有物品损失证据。完整页面确认需先补齐真实背包阶段正负例，不能凭坐标或地点 OCR 缺失推断可以继续出售 |
| 优先 | R3 保留目录大小写、R8 输入释放失败 | 分别影响用户证据和异常退出后的输入状态，应修。释放必须逐项尝试并处理失败；当前 PyDirectInput 的 keyUp 返回布尔值，但 mouseUp 正常返回 None，不能简单把所有 None 都判失败 |
| 随后 | R4 启动已有 150302 | 属于此前弹窗修复遗漏的入口，应补传现有会话 OCR 并测试启动到关闭续接，保持完整错误码校验 |
| 随后 | R5 INI 保存、R6 整数校验、R7 更新结果缓存 | 都有明确失败反例，值得修；主要出现在手改/导入配置或非关键缓存损坏时，并非已知黄条漏按的原因。结果缓存可降级，更新事务 pending/journal 不能因此放宽 |
| 可延后 | QTE 与等待流程的职责拆分 | 有维护收益，但不能代替上面的功能修复；不为质量评分整体重写，不顺带改变输入时序 |

## 验收边界

同一源码审查已完成 574 项离线回归、Ruff、架构与隐藏 UI 等检查；本次未改业务代码，因此没有无变化地再跑整套测试。八项反例的重新复现说明现有测试仍有覆盖空缺，测试全绿不能证明没有缺陷。

后续闭环应分别记录：反例转回归并修复 → 完整离线检查 → 候选包核对 → 对应原场景实机验证。QTE 还须区分“获得按键许可”“输入已发送”“游戏判为命中”和“确认捕获”。没有对应证据的项目保持待验证；本次没有构建、部署或发布。
