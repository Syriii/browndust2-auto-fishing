## 结论与范围

本轮直接核查源码、实际 Tk 界面与本机 EXE，未使用第三方代码评分技能。工作区原有未提交改动保留。自动静态检查覆盖业务包、入口、脚本和测试，另核查依赖声明、锁定文件和两份 CI。人工重点沿 UI 渲染、任务启动、取消及释放、鱼获事务、配置和更新链路检查；不宣称穷尽每个分支或完成游戏实测。

性能脚本 `scripts/checks/benchmark_ui.py` 使用临时配置和内存鱼获库，计时包含 `root.update()`，输出中位数、P95、最大值及 cProfile 调用栈。初次两份并行运行数据仅用于定位，正式前后对比使用单进程报告。计时受当前机器负载、窗口遮挡、系统缓存和 profiler 影响，不能等同于屏幕帧率。

第一轮单进程基线：打开图鉴 887.62 ms、进入目标选择 940.75 ms；40 次选目标中位数 299.79 ms、取消 234.06 ms；切页中位数 205.94 ms。最终数据见本次交付记录。去掉圆角主题的诊断实验仍可复现明显 Tk 重绘开销，因此没有把更换配色当作解决性能的依据。

视觉采用浅灰白、系统蓝、圆角、高光边缘与低对比层次。当前 Tk 版本实现磨砂质感，不提供桌面背景实时模糊；没有加入跨进程截图或通过全窗口透明度降低文字清晰度。持续动画与真正透明背景需要单独的渲染方案，不能用换色冒充。

## 其他性能与维护风险

- `CatchesPage._reference` 在 UI 线程读证据、进行未知鱼图关联；历史首次加载可能阻塞。按记录 ID 后台解析并经主线程投递会更合适；仍需防旧筛选结果覆盖新筛选。
- `FishingJournal.history` 以 julianday(caught_at) 排序，`history_dates` 对历史日期去重；目前没有覆盖该排序的索引，大量记录需要数据集基准与查询计划验证，不能凭小样本推断长年使用表现。
- `SessionCatches.refresh` 重建最近 30 条的问题已在 0.4.8 改为按 ID 增量更新，回归覆盖已有卡片保留；其他大历史库性能风险仍保留。
- `qte.py` 789 行、`FishingBot.wait_for_bite` 117 行，控制、恢复与取证修改耦合较高。分阶段抽取纯状态计算，保持 RunStopped(BaseException)、窗口保护、共享 OCR 锁与有界后台写入。
- 当前 CI 包含离线回归、Ruff、架构及构建，但没有 UI 性能门槛；新增基准保留操作耗时，后续可在固定硬件单独执行。普通共享 CI 不宜把桌面渲染毫秒数设为硬门槛。
