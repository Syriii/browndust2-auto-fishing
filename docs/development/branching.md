# 分支、版本与发布约定

[文档目录](../README.md) · [构建与发布](releasing.md)

采用 `main` + 短期功能分支 + 版本标签，不维护长期 `dev` 分支。

| 对象 | 用途 | 生命周期 |
| --- | --- | --- |
| `main` | 已完成检查的集成代码 | 长期保留 |
| `feat/<功能>` | 新功能开发与评审 | 合并后删除 |
| `fix/<问题>` | 问题修复与回归 | 合并后删除 |
| `docs/<主题>` | 独立文档调整 | 合并后删除 |
| `v主.次.修订` 标签 | 固定发布对应的提交 | 长期保留，不移动已发布标签 |
| GitHub Release | 版本说明和下载附件 | 按版本保留 |

合并 main 不等于发布。可以合并多组改动，验证后再发布一次；增长的是提交历史、标签和 Release，
不会为了每个版本长期保留一个分支。删除已合并分支不删除已进入 main 的提交记录。

## 日常变更

1. 同步 main，从它建立本次功能或修复分支。正在进行的工作及时提交，不把多轮改动长期留在工作区。
2. 更新实现、必要回归和相应文档；记录离线验证与游戏实测各自覆盖的范围。
3. 推送分支，创建针对 main 的 PR。相关 CI 必须通过，再合并。
4. 删除已合并的临时分支，本地 main 快进到远程 main。尚未合并的分支不自动删除。

提交身份使用维护者本人。构建目录、个人配置、运行日志、更新缓存和维护工具凭据不提交；
作为回归依据的截图需放在 tests/fixtures，并记录来源。

## 版本发布

版本号以 pyproject.toml 的 project.version 为准，首轮更新协议使用三段数字，如 `0.2.0`。
标签相应为 `v0.2.0`。新功能增加次版本，兼容修复增加修订版本；出现不兼容变化时明确迁移要求。

从验证完成的 main 提交创建标签和 Release。当前发布工作流在 Release 发布时测试、构建并上传完整 ZIP
及 `.zip.sha256`；发布后要确认两项附件齐全、哈希匹配、程序可读取 Release 版本信息，才能报告交付完成。
仅创建标签或合并 main 不会自动发布 Release。需要预先构建时可以手动运行 Build Release Package。

测试发布可标记 pre-release，但当前程序只检查正式 Release，尚无测试更新渠道。
已经发布的附件不随 main 后续提交改变；修复已发布版本时发布新版本，不覆盖或挪动旧标签。

## 文档同步

- 用户行为变化：更新 docs/user；目录和更新方式变化同步 README。
- 开发/发布步骤变化：更新本页、releasing.md 和实际工作流，保证三者一致。
- 每次发布：更新 CHANGELOG，写清新增功能、修复、兼容性和验证限制。
- 后续纯文档提交：可以独立合入 main，不必发布新的 EXE 或 Release。

参考：[GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)。
