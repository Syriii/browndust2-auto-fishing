# 机制规则与当前覆盖

2026-09-14：统一目录登记 13 类技能及绿色维持输入模式，共 14 项。鱼种可能携带的机制按来源并集；多个机制可叠加。所有钓场共用检测和响应入口，鱼名、岛屿、稀有度与攻略列表均不用于启停机制；不另造一份天空岛规则。目录表示已知规则范围，不代表 14 项均已识别、自动解除或实机验收。

| --- | --- | --- |

| `shell` 贝壳 | 排除所有已定位贝壳及边距，目标膨胀不能跨回遮挡 | 有真实模板与留出图回归；遮挡变化和完全不可见场景仍需实测 |
| `ink` 墨汁 | 降低可见性时不猜光标，不将目标漏检直接视为正常空场景 | 当前可见性保护；墨迹身份、范围、消退尚未独立识别 |
| `invisible` 隐形 | 定位不可信时等待并留证 | 无盲按；尚无可靠隐形轨迹恢复，不保证该阶段能输出伤害 |
| `freeze` 冰冻 | 资料图明确 3→2→1；按一次观察一次，解除后不补按 | 已接入后台冰蓝外观与计数字形候选，连续出现独立留证；3 有独立来源正例，1/2 只有模板同源图。没有可信冻结／解除连续序列，破冰输入尚未启用 |
| `wall` 反弹壁 | 同帧读取全部墙，以当前指针所在的可达区间选目标 | 已移入公共控制层，六钓场都应用多墙交集；墙内不投影，墙体阻止重叠泡泡输入并释放受阻绿色持有。原始像素支持检查排除黄条纹理和压缩光标误识别。碰撞方向跟踪与实际解除仍待实测 |
| `clones` 分身 | 比较窄竖线形状与亮度，选择唯一可信真指针 | 共用定位，亮度歧义时不按；交叠、隐形叠加仍可能无定位 |
| `bubble` 泡泡 | 每个球独立确认，可信指针位于球内才尝试一次 | 支持多个球与残影去重；动作后消失不等于成功解除；满遮挡和超时效果仍需验证 |
| `yellow_hide` 黄区消失 | 连续确认有效黄区缺失后，选择安全蓝区 | 两策略共用蓝区确认及同次入区去重；不使用旧攻略的固定恢复时钟 |
| `poison` 毒海浪／反甲 | 紫色候选按局部障碍避让，记录扣时和消退 | 局部避让；不主动点掉。来源争议保留，不硬编码惩罚数值 |
| `slow` 减速／麻痹 | 重新读取当前位置，不沿用恒定速度外推 | 普通定位可继续；无独立技能消退识别，慢指针与贝壳叠加需继续验收 |

天空岛六种稀有／传说鱼使用上表已有的加速、墨汁、咬人、分身、紫色、绿条、蓝锁、黄隐、减速组合。按目录覆盖准备即可，不能因此宣称天空岛所有鱼已经能自动钓上来，绿色完整处理仍是明确缺口。

## 输入仲裁与未知记录

优先处理取消、失焦与已持有按键的释放；绿色持有期间独占输入；其他动作依可信位置、障碍、连续确认与生命周期选择，每帧最多一个意图。不让图鉴预期机制、后台 OCR 或观察器线索直接派发按键。

`BaseQTEStrategy` 统一构建墙体检测器、合并墙体与其他遮挡、调用 `MechanismPolicy`，再处理普通黄蓝目标。`MechanismRegions.wall_rects` 保存当帧结果，仲裁和普通目标共用一次检测，不跨帧缓存旧墙。现有两个地点类只保留黄条面积阈值差异，没有各自的特殊机制分支。墙体候选的首次及组合控制图同样进入正常取证。

独立观察器也通过 `BlockerDetector.from_config` 使用相同的配置缩放和识别规则，读取已有观察帧；不获取额外截图或复用另一时刻的控制坐标。`wall_candidate` 可触发场景记录，`wall_rects` 保存矩形，`appearance_lifecycle` 记录各墙候选出现／消失／未知，根元数据 `wall_detector` 保留本次阈值。没有按键或失败同样可留证；墙消失仍不证明碰撞或成功解除。

本轮为场景证据增加 `mechanism_catalogue_revision` 和每帧 `mechanism_review`，包含可能对应的机制、未映射线索和未确认身份。绿色候选可对应泡泡或绿条；亮指针缺失可对应墨汁、隐形、分身，也可能不是技能，因此仍然标 `unconfirmed`。

原有低频时间线持续保存没有已知线索的 QTE；未知机制不需要先命中识别器才有机会留图。空线索只表示“未匹配”，不表示普通场景或捕获成功。仍受 80 帧、12 MB、分段数、队列及磁盘轮转限制；短暂事件或严重遮挡可能漏样。复用观察帧，后台编码写盘，无新增控制截图、OCR、同步写盘或排队输入。

冰冻观察补充：`freeze_counter_1/2/3` 只生成候选事件；`freeze_counter` 保存数字、范围、得分和 `confirmed=false`。它与左侧整轮倒计时分开，属于 QTE 指针附近的冰晶。计数变化保留逐帧证据，`freeze_candidate` 外观生命周期只说明出现／消失，不能把数字消失当成成功破冰。

候选采用计数红色描边与周围冰蓝外观双重依据，匹配数字间差异不足时保持未知。独立巴哈图的 3 在 0.5–2 倍缩放下可检出，同组 11 张其他机制图未误认。GameKee 的 1/2/3 同源图只用于实现检查，不能充当三阶段独立验收；未据此给控制线程新增按键分支。

## 下一步验收顺序

用户已于 2026-09-14 将冰冻、绿色两项改为日常使用中遇到后再反馈，不安排专门演示。下列条目是后续证据的验收标准，不是要求现在手动触发技能；先使用正常场景取证，缺失部分保持待验证。其他资料、机制及图鉴工作不依赖这两项演示。

1. 冰冻：真实冻结前、3/2/1 每次变化及解除连续帧，含牙齿、计时数字、泡泡负例。按键按“当前已确认阶段→一次输入→等待画面变化”执行；不得看到一张 3 就盲发三键。
2. 绿色：核实深色起按端的局部几何及真实指针方向，覆盖蓝绿并存、紫色叠加、窄区和丢帧；通过后才给真实图填 `entry`。控制器已有保护不等于起按识别已实现。
3. 墨汁／隐形／加减速：补足可见性、帧龄与轨迹变化的正负连续例；新增预测必须有误差边界，不能靠攻略时长外推。
4. 多墙与现有组合：验证多墙实际游戏场景、墙与指针重叠、消失及碰撞反向。GameKee 压缩光标反例与 Y05／Y39 黄条纹理已通过原始像素支持检查修复；巴哈和 GameKee 条体正例保留墙体定位。稀疏、遮挡墙可能仍漏检，不能据这些静态样本宣布完整碰撞跟踪通过。
5. 记录动作时刻、独立机制生命周期、普通 HIT/CRITICAL 和结算结果。区分“尝试”“外观消失”“确认解除”“确认捕获”，不以一次捕获验收所有机制。

旧八项全量审查问题不由本轮资料库或多墙修复自动关闭，继续见[审查报告](../../development/code-review-2026-09-14.md)。
